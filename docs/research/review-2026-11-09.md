## A. POLICY / EVASION CREEP

**A1 — MEDIUM — read-only JavaScript is evaluated on live x.com pages, beyond the stated "no JS injection" line.**
`browser.collect_tells` calls `page.evaluate(_TELLS_SCRIPT)` on the live page (`browser.py:665-672`); `diagnose._dialog_html` calls `locator.evaluate("el => el.outerHTML")` on the live composer (`diagnose.py:475-487`, line 482); every human click calls `locator.evaluate` for `scrollIntoView` (`poster.py:130-133`) and `document.elementFromPoint` (`poster.py:149-161`). These are read-only (no property patching, no `add_init_script`, no persistent init script, no `add_script_tag`), so this is a *literal-policy* deviation rather than stealth tooling. Fix: state in the policy doc that read-only diagnostic/hit-test `evaluate` is permitted and why; or remove them (`page.content()` for the dialog; Playwright's own actionability for the hit test). Add a test that greps for `add_init_script`, `add_script_tag`, `set_extra_http_headers`, `user_agent=`, `locale=`, `timezone_id=`, `route(` and `fetch(` in `src/` and fails if they appear.

**A2 — PASS — no user-agent / webdriver / plugin / WebGL / screen / timezone / locale spoofing, no CAPTCHA solving, no proxy, no password auto-login, no fabricated `x-client-*`/`x-csrf` headers, no direct GraphQL/API calls.**
`build_launch_kwargs` only removes `--enable-automation` (allowed) and adds `--disable-blink-features=AutomationControlled` (allowed) (`browser.py:249-268`; tests `test_browser.py:302-357`). There is no `user_agent`, `locale`, `timezone_id`, `geolocation`, `permissions`, `extra_http_headers`, `proxy`, `add_init_script` or `add_script_tag` in `src/` (grep). `PlainLogin` is an ordinary Chrome process with a URL and no credential handling (`browser.py:518-603`). The only network reads are `page.on("response")` observation of the page's own `CreateTweet`/`DeleteTweet` (`poster.py:267-313`), and the only writes are cookie restore (`sessions.py:548-565`) and `storage_state` capture (`sessions.py:526-545`). The viewport/window size (`browser.py:68,71,265`) is a layout choice, not screen spoofing.

## B. SECRETS

**B1 — MEDIUM — failure evidence is unsanitised and not 0600; `page.content()` can persist CSRF/meta/hidden-input token material.**
`_capture_artifacts` writes the full DOM with `write_text` (default 0644) into a 0700 directory (`poster.py:1164-1177`); screenshots are likewise created by Playwright with default mode. `diagnose.sanitise_html` redacts only `<input type=password>` values (`diagnose.py:168-183`), not hidden inputs, `<meta name="csrf-token">`, inline session JSON, or `ct0`-shaped values. `new_artifacts_dir` creates 0700 dirs (`store.py:238-259`) but never chmods files; `doctor`'s permissions check only checks directories and named credential files, not artifact files (`diagnose.py:235-287`). A cookie value is not normally in the DOM, but a CSRF token can be. Fix: write each artifact through a 0600 helper; sanitise hidden-input values and csrf/meta keys; extend `_permissions_check` to artifact files; document that artifacts still contain page content.

**B2 — LOW — `--verbose` prints full tracebacks, including chained Playwright messages.**
`_call` calls `traceback.print_exc()` (`cli.py:573-582`); no locals are printed, and `_redact` still applies to the final message (`cli.py:715-722`), but a Playwright error string is third-party text. I found no path that puts a cookie value into such a message. Fix: add a canary-in-error test for `--verbose` (there is one for status/doctor/ledger, `test_cli.py:651-691`).

**B3 — PASS — credential stores are private and cookie-free where required.**
`storage_state.json` and `.bak` 0600 with temp-file + fsync + `os.replace` (`store.py:110-128,373-389`); ledger 0600 (`ledger.py:496-511`, test `test_ledger.py:313-316`); `session.json`, `parked.json`, `session.lock` 0600 (`store.py:154-166,180-205,89-91`); home/profile/artifacts dirs 0700 (`store.py:68-77,238-259`). `SessionSummary` carries only booleans/timestamps/handle (`models.py:136-166`; `store.py:279-331`). No Playwright trace, HAR or video is configured (`src/` has no `tracing`, `record_har`, `record_video`). Ledger and CLI redact `auth_token|ct0|password|secret|api_key|Bearer` (`ledger.py:35-79`; `cli.py:65-68,715-722`). The successful-thread test asserts both canaries are absent from logs, ledger, meta, artifacts and serialized output, with a control showing the canary is present in `storage_state` (`test_poster.py:701+`).

**B4 — LOW — artifact retention is count-only, no age cap.**
`keep_artifacts=10` (`config.py:114`) and pruning keeps the newest ten (`store.py:358-366`). Old screenshots/HTML can retain account/page content indefinitely if no further runs create artifacts. Fix: prune by age as well, and document.

## C. IDEMPOTENCY / DOUBLE-POST

**C1 — BLOCKER — a click that lands and then the process dies before any id is recorded re-posts on the next run.**
The click barrier (`_Attempt.clicked`) exists only in memory (`poster.py:324-337`); it is set immediately before `_click` (`poster.py:726-727`). `post_thread` catches only `Exception` (`poster.py:494`), so `KeyboardInterrupt`/`asyncio.CancelledError` (BaseException) skip `_record_failure`. The ledger row stays `PENDING` with zero recorded tweets. `Ledger.decide` treats a `PENDING` entry with no posted tweets as `NEW` (`ledger.py:202-208`), so the next run launches Chrome and posts the same thread again. This is the exact "click landed but response not seen" case in the checklist, and `kill -9`/power loss is even less recoverable. The probe confirmed `PENDING`-zero → `NEW`. Fix: persist a `click_started_at` (or `CLICKING` status) immediately *before* `_click`; treat a `PENDING` with a click marker, or older than a short threshold, as `BLOCKED_UNKNOWN`; downgrade only on a proven pre-click failure; also call `_record_failure` from a `BaseException` handler (or wrap `asyncio.run`/CLI). Add a test that patches `_click` to click then raise `KeyboardInterrupt` before any response and asserts the rerun blocks.

Related false-quarantine: `clicked=True` is set before `_click`, so a click that fails before dispatch (no box, covered overlay) marks the thread `UNKNOWN` although nothing was posted (`poster.py:726-727,859-873`). That is safe but noisy; a separate "request dispatched" marker is better.

**C2 — BLOCKER — `--force` on an `UNKNOWN` entry that already has recorded tweets wipes them and re-posts them.**
`decide` returns `NEW` for `UNKNOWN` when `force=True` (`ledger.py:204-205`) before it checks `entry.posted` (`ledger.py:206-208`); `begin` preserves `posted` only for `PENDING`/`FAILED` (`ledger.py:220-225`), so the forced run starts with `posted=()`. The module docstring explicitly claims the opposite (`ledger.py:195-197`). The poster test demonstrates the duplicate: a composer thread fails at tweet 2 with tweet 0 recorded; `set_scenario(OK)` disables the fake's duplicate rejection (`tests/fake_x/site.py:344-378`), `force=True` re-posts all three, and the test asserts only `forced.complete is True` (`test_poster.py:443-464`) — the fake would hold `One` twice. The same transition is asserted as intended in `test_ledger.py:116-120`; `test_begin_after_forced_repost_starts_clean` covers only `POSTED` (`test_ledger.py:154-163`). Fix: check `entry.posted` before the `UNKNOWN` branch and return `RESUME` (or refuse) for a partially posted thread; preserve `posted` in `begin` for every status; make `--force` on a partial entry require an explicit "I verified nothing is live" flag; assert `len(fake.tweets)==3` in the test.

**C3 — HIGH — ledger writes are file-fsynced but not directory-fsynced; power loss can lose the PENDING rename.**
`Ledger._save` fsyncs the temp file and `os.replace`s (`ledger.py:496-511`), but never fsyncs the parent directory, unlike `SessionStore._write_bytes` (`store.py:389`). On a crash, the rename may not be durable; the next run may see no PENDING row and post. Fix: call the same `_fsync_dir(path.parent)` after replace; add a fault-injection test.

**C4 — HIGH — a corrupt ledger is quarantined and treated as empty, destroying all duplicate evidence.**
`_load` moves unreadable/JSON-invalid/non-object files to `.corrupt` and returns `_State()` (`ledger.py:427-439,513-516`); every POSTED entry then disappears and any thread can be posted again. This is deliberate ("refusing to start would block every future post") but unsafe for a posting tool. Fix: if the file is non-empty and unparseable, write a park marker / refuse with an actionable message and require an explicit `--reset-ledger`; or keep the old file and require manual resolution. The current test asserts the empty behaviour (`test_ledger.py:186+`), so it would need changing.

**C5 — MEDIUM — `content_hash` ignores media contents and alt text, and the CLI never sets `Thread.key`.**
The hash covers `key`, tweet text and media *file names* (`models.py:29-58`); an image replaced under the same name or changed `alt_texts` (`models.py:26`, never used) does not change it. The CLI constructs `Thread` with the default empty key (`cli.py:379`), and `post_text` hardcodes `key=""` (`poster.py:543-545`), so deliberately posting identical text a week later is refused as `ALREADY_POSTED` unless `--force` is used — and `--force` is the unsafe path in C2. Fix: add `--key`/`--allow-repeat`; include media size (or a cheap digest) and alt text in the hash; document the intended repeat workflow.

**C6 — MEDIUM — `--force` on a POSTED thread overwrites the POSTED record instead of appending history.**
`begin` resets `posted`, `started_at` and `completed` for a forced re-post (`ledger.py:220-225`); if that run then fails before completion, the ledger no longer proves the original post, and the old tweet ids are lost. Fix: keep an append-only `attempts` list or a `history` field; never discard a previous `completed` record.

**C7 — LOW — two-process exclusion relies on the non-blocking flock; the loser exits rather than waits.**
`SessionStore.lock` is correct (`store.py:79-108`), and a second process cannot enter `authenticated_page`; but because `decide` runs before the lock, the only reason this is safe is that the loser gets `SessionBusyError` and does not retry. That is acceptable but should be explicit in docs: never wrap `xposter post` in an auto-retry loop.

## D. PARK-NEVER-RETRY

**D1 — HIGH — during posting, a challenge that is only an iframe/selector overlay is not detected; the run ends `UNKNOWN` and the next run proceeds instead of parking.**
`sessions._probe_login` checks `challenge_dialog` and `challenge_iframe` before the logged-in indicator (`sessions.py:424-450`), but `poster._page_verdict`, used by the response-wait probe and the delete timeout, checks only `classify_url` and the entire body's `inner_text` (`poster.py:899-911`). If the "Verify you are a human" text lives inside the Arkose iframe, or the dialog has no text in the top document, the verdict is `None`; `_click_and_capture` eventually raises `PostOutcomeUnknownError` (`poster.py:756-772`) and no park marker is written. Fix: call the same challenge-selector probe from `_page_verdict` (and any wait loop) and park immediately; add an iframe-only challenge test.

**D2 — HIGH — unrecognised error codes/messages default to `RETRY`, contradicting the "only capacity errors retry" rule.**
`_classify_error_item` returns `RETRY` for any code/message not in the tables (`guard.py:428-435`). Codes documented in `web-client.md:204-232` but absent from the tables — 179 `StatusViewForbidden`, 220 `RestrictedAuthToken`, 261 `AppInReadOnlyMode`, 349 DM error, 386 attachment limit, 408 invalid URL, 433 conversation control, 445 read-only token — would get one re-click before parking. That is exactly the "retry escalates" pattern the module docstring forbids (`guard.py:10-15`). Fix: make an unknown code `STOP_THREAD`/`PARK` (no retry), or add the complete observed table; keep `RETRY` only for 88/131, HTTP 5xx and explicit message rules. Test 261 and 179.

**D3 — HIGH — an HTTP 403 with no parseable body becomes `RELOGIN`, not a park.**
`classify_http_status(403)` returns `RELOGIN` (`guard.py:470-476`); when the body is HTML (Cloudflare/interstitial) or empty, `_inspect` keeps that verdict, `_raise_for_verdict` raises `NotLoggedInError`, and `park_on` deliberately does not park login errors (`sessions.py:254-267`). The next run starts Chrome again and retries, escalating. `risk-and-limits.md:299-315` says a 403/226 is a behavioural block and must stop/park. Fix: classify an unparsed 403 as `PARK`/challenge, and only map body codes 32/89/135/215/403 to `RELOGIN`; keep 401 as relogin. Add a fake scenario for 403 + 226 and 403 + HTML.

**D4 — MEDIUM — body-wide text heuristics can park a healthy account because a timeline/status post contains "captcha" or "authenticate".**
`_TEXT_RULES` includes the bare needles `"authenticate"` and `"captcha"` (`guard.py:263-276`), and `_page_verdict` runs `classify_text` over the entire `body` (`poster.py:907-911`), which on `/home` and on a status page includes other users' posts. A user tweeting about a CAPTCHA would park the tool. Similarly `"account locked"` and `"something went wrong"` are broad. Fix: scope text classification to known alert/dialog/toast containers, or require a visible challenge selector or a URL/API-code signal; keep the broad text rules only for the login/probe path. Add a negative test with a timeline post containing the word.

**D5 — LOW — URL substring matching can relogin/park on query-string text.**
`classify_url` lowercases the whole URL and tests `"/login"`, `"/logout"`, `"/suspended"` anywhere (`guard.py:494-531`), so a redirect URL with `?next=/login` would be treated as an auth redirect. Fix: match `urlsplit(url).path` exactly/prefix, not the full string.

**D6 — LOW — the single 5xx re-click waits only 0.4–1.4 s.**
The retry condition itself is correct: one retry, only when a CreateTweet 5xx was seen and no tweet was captured (`poster.py:746-752`); but the pause is `action_pause_s` (`config.py:47`), while `risk-and-limits.md:309` recommends 30–60 s for the generic transient failure. Fix: sleep a dedicated 30 s (or 15–45 s) backoff before the re-click.

**D7 — LOW — `_refuse_disabled` returns on a Playwright error and lets the click proceed with unknown disabled state** (`poster.py:975-978`). If the button is detached/covered, the subsequent click fails, so the practical risk is low, but the safe behaviour is to raise `UiChangedError` instead of returning.

**D8 — PASS — no other retry loops.** The replies loop is sequential progress, not retry; `_wait_until`/`_refuse_disabled` poll selectors, not network; 429 parks (`guard.py:477-483`); the only re-click is D6. A challenge after a click marks `UNKNOWN` and `authenticated_page` parks on the typed `ChallengeError`/`RateLimitedError` (`sessions.py:316-323`).

## E. SESSION LIFECYCLE

**E1 — MEDIUM — `xposter login` runs the plain Chrome window without the store lock.**
`sessions.login` calls `PlainLogin.run` before `verify` (`sessions.py:348-375`); `PlainLogin.run` only checks `_profile_in_use` (`browser.py:563-564`), which reads Chrome's `SingletonLock`. Two simultaneous logins, or a login while a posting run is starting, can race before Chrome writes that link; the second process can open the same `user-data-dir` and corrupt it. Fix: wrap the `PlainLogin.run` call in `store.lock()`; a second login should fail with `SessionBusyError`, not race.

**E2 — MEDIUM — a corrupt non-empty profile has no repair path.**
Backup cookies are restored only when the profile directory is empty (`sessions.py:292-298`); `wipe_session` exists (`store.py:261-277`) but there is no CLI command for it (the CLI has `login/status/verify/refresh/unpark/post/delete/ledger/doctor`, `cli.py:147-556`). A profile corrupted by a Chrome crash or a concurrent run leaves `login` failing at launch with only a generic "close other Chrome windows" message (`browser.py:425-453`). Fix: add `xposter logout`/`--reset-profile` that calls `wipe_session` after confirmation, and a `doctor` repair hint; test the corrupt-non-empty case.

**E3 — MEDIUM — the default display on macOS/Windows is headless, so the first run's UA advertises `HeadlessChrome`.**
`resolve_display` returns `HEADLESS` for non-Linux AUTO (`browser.py:224-226`); my local probe with the shipped launch kwargs on Chrome 156 produced `navigator.webdriver=false` but `... HeadlessChrome/156.0.0.0 ...`, `outer==inner`, and `screen==1440x900` (matching `test_browser_integration.py:87-98`). `assess_tells` labels that "note", not "warn" (`browser.py:703-714,738-744`), and `risk-and-limits.md:246` calls the headless marker "moderate if headless". Fix: default `post` to `VISIBLE` on macOS/Windows (or make `doctor --tells` fail for posting when the UA has `HeadlessChrome`), and document `--display visible` for the first run.

**E4 — LOW — stale `SingletonLock` pid reuse can report a false "profile busy".**
`_profile_in_use` reads the pid from the symlink and only checks `os.kill(pid, 0)` (`browser.py:379-417`); if the pid has been recycled by an unrelated process, the profile is falsely busy. Fix: verify the process name/argv contains Chrome, or fall through to Chrome's own recovery.

**E5 — LOW — `refresh --force` bypasses `min_interval_s`.**
`due = force or ...` (`sessions.py:394-399`; CLI `cli.py:242-252`), so a cron using `--force` can refresh more often than the policy. The plain cadence itself is correct (12 h default, `config.py:74`). Fix: document that timers must call `refresh` without `--force`; optionally rate-limit forced refreshes.

**E6 — LOW — a Chrome update that Playwright cannot drive is reported as "close other Chrome windows".**
`_launch_error` maps every unrecognised launch failure to that advice (`browser.py:425-453`); a `chrome --version` vs Playwright incompatibility would be misdiagnosed. Fix: include the Chrome version and a "try `playwright install`/update Playwright" hint when the error is not a singleton error.

**E7 — PASS — lock/stale-lock, normal-Chrome-in-use, backup preservation and keepalive behaviour.**
`flock` is released on process death, so a stale lock file is harmless; the pid content is diagnostic (`store.py:79-108`). A normal Chrome on the same profile is detected by the SingletonLock (`browser.py:477-478,563-564`; tests `test_browser.py:835-873`). A failing body leaves the old `storage_state` untouched (`sessions.py:316-323`; `test_sessions.py:425-440`). Keepalive only navigates to `/home` and scrolls (no clicks), bounded by the policy window (`sessions.py:685-711`).

## F. CORRECTNESS vs RESEARCH

**F1 — MEDIUM — the newline behaviour is an unverified premise stated as fact in code.**
`_type` uses `Shift+Enter` for line breaks and the docstring says "on x.com a bare Return submits the post" (`poster.py:997-1015`). `web-client.md:48` does say "Enter triggers `form.requestSubmit()`", but neither research doc records a live test of Shift+Enter, and the offline fake is written to *model* the assumption (it swallows bare Return, `tests/fake_x/pages.py:206-217`). The fix itself is right (Shift+Enter is the safe choice); mark it `INFERRED/UNVERIFIED` in the docs and verify it in the first live calibration (type a two-line post, confirm no request before the click).

**F2 — MEDIUM — the error table is incomplete and conflates HTTP 403 with GraphQL code 403.**
`_RELOGIN_CODES` includes code 403 as `IneligibleFor2faAfterModification` (`guard.py:137-143`), while `classify_http_status` uses HTTP 403 for "session may be invalid" (`guard.py:470-476`); these are different layers. Several codes in `web-client.md:204-232` (179, 220, 261, 349, 386, 408, 433, 445) are missing and fall into D2's retry-by-default. Fix: separate `http_status` and `body_code` tables, add the missing codes, and make the tests cover each row of the research table.

**F3 — MEDIUM — `Tweet.alt_texts` is modelled but never applied.**
`models.py:22-26` carries alt texts; `_attach_media` only uploads files and waits for previews (`poster.py:1017-1043`); the alt selectors exist (`selectors.py:132-153`) and the research describes the "Add ... description" flow (`web-client.md:58-61,352`). A caller setting alt texts gets silently ignored content. Fix: implement the alt editor in `_attach_media` (or remove the field and document that alt text is unsupported).

**F4 — LOW — `_POST_WAIT_S_PER_TWEET=15` allows 375 s for a 25-tweet `Post all`.**
The comment at `poster.py:59-61` is right that a fixed 15 s total is wrong, but the total has no research basis; `risk-and-limits.md:286` targets ≤15 min per thread. This is a wait bound, not a safety issue; document it.

**F5 — LOW — the splitter's URL rule is narrower than the doc's "every URL weighs 23".**
`splitter.py:46-70` recognises only a fixed TLD list; `https://example.museum` is counted per character, so the module can over-count and split a tweet X would accept. This is conservative (never over-posts) but contradicts the stated invariant at `splitter.py:5-13`. Fix: document the approximation or extend the list/URL parser.

**F6 — LOW — the `Post all` fallback includes "Schedule".**
`composer_post_all_button` falls back to `button:text-is("Schedule")` (`selectors.py:83-90`); if `Post all` is absent but a Schedule button is present, the driver would schedule the thread instead of posting it, with no visible error. Fix: remove `Schedule` from the fallback (or assert the text at click time).

**F7 — GOOD — the core wire assumptions match the research.**
CreateTweet and note-tweet detection (`guard.py:589-641`) match `web-client.md:96-166`; the 25-item cap (`poster.py:57-58`) matches §6; the park/retry/reject code sets match §3; the ct0/353 path waits for X's own retry instead of forging a header (`poster.py:737-745`) matches §5.2; no direct API calls. The fake's success shape (`tests/fake_x/site.py:380-406`) mirrors `tweet_results.rest_id` + `result.rest_id` and `notetweet_create`.

**F8 — LOW — `nav_profile_link`'s primary selector is literally `a[href="/<screen_name>"]`** (`selectors.py:214-223`), which can never match a real handle; `_profile_handle` therefore relies on `_nav_handle` scanning later (`sessions.py:583-628`). It works on the fake, but the selector is dead documentation. Fix: build the handle selector in code (`f'a[href="/{handle}"]'`) or delete it from the table.

## G. HUMAN-LIKE BEHAVIOUR WITHOUT SPOOFING

**G1 — MEDIUM — the default composer strategy posts an N-tweet thread in one "Post all" burst; the 20–45 s between-tweet gap is only used by the replies strategy.**
`_post_composer` types each item with a `think` pause 2–6 s and then one submit (`poster.py:583-610`), while `_post_replies` waits `between_tweet` before each reply (`poster.py:646`). A 25-tweet default thread therefore lands within seconds of the first request, unlike the recommended cadence (`risk-and-limits.md:285-286`). It is X's own client behaviour (the researched `Post all` loop, `web-client.md:168-182`), but it is still a burst. Fix: default to `REPLIES` above a small threshold (e.g. 4 tweets), or document that Composer is a deliberate exception and prefer Replies for the weekly thread.

**G2 — MEDIUM — a 25-tweet replies thread can exceed the research's ≤15-minute target before typing is counted.**
24 gaps at 20–45 s = 8–18 min (`config.py:46`), plus ~6–10 min of typing (35–120 ms/grapheme, `humanize.py:293-309`), plus 2–6 s think pauses per item, plus pre-submit dwell. The risk memo targets ≤15 min for 25 tweets (`risk-and-limits.md:286`). Fix: cap the inter-tweet range (e.g. 18–32 s) or enforce a total-thread budget in the pacer; at minimum document that 25-tweet replies exceed the target.

**G3 — PASS — timings and pointer paths are varied, not robotic.**
Typing is per grapheme with a log-normal-ish 35–120 ms delay, longer after spaces/punctuation, occasional 300–900 ms hesitations (`humanize.py:293-309`); pauses are uniform ranges drawn from an injected RNG; mouse paths are cubic Bezier with ease-in-out spacing, normal jitter and Gaussian click offsets clamped to 15–85 % (`humanize.py:195-257`); scroll plans are 2–4 wheel steps with a partial back-scroll (`humanize.py:178-193`). Polls are 50 ms/0.5 s, not fixed multi-second sleeps. The only regularity is `_PROBE_INTERVAL_S`/`_POLL_INTERVAL_S`, which are internal, not page-visible.

**G4 — LOW — the first click's pointer path starts at `(0,0)`.**
`_mouse` is initialised to the top-left (`poster.py:370`) and the first `human_click` interpolates from there (`poster.py:1067-1074`), producing a long diagonal from the screen corner. Fix: seed it with a plausible viewport point (or random start near the first target) after the page loads.

**G5 — LOW — keepalive uses module-level `random`, not the injected Humanizer RNG.**
